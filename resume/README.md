## インフラ 運用保守
### プロジェクト概要

| 項目 | 内容 |
|--- |--- |
| 期間 | 2024年4月 〜 現在 |
| プロジェクトカテゴリ | Webサービス / 自社プロダクト |
| プロジェクト概要 | 社内で開発されたWebサービスのインフラ運用保守 |
| 担当工程 | クラウド環境のメンテナンス |
| ロール | メンバー / インフラ |
| 開発体制 | 運用保守2名 |
| 開発手法  | スクラム |
| 技術スタック | EC2, RDS, S3, EFS, ECS, ECR, Lambda, EventBrige, CloudWatch, ALB, SQS |
| 周辺ツール | 管理ツール： Mackerel<br>タスク管理： GitHubProjects,<br>数値計測： Redash |

### 課題
前任のインフラ担当が退職したことで、各種インフラリソースがメンテナンスされないまま放置されている状況が続いていました。社内ではCTO以外にインフラに精通したメンバーがおらず、適切な管理やアップデートが行えない状態に。
そこで、前職でサーバー構築経験があった私がアサインされ、インフラのリソース改善を進めることになりました。

特に以下のような課題がありました：
- 古いバージョンのRDS（MySQL 5系）を使用しており、AWSのサポート終了が迫っていた
- CentOSのサポート停止に伴い、OSの移行が必要だった
- アプリケーションサーバーに対するDoS攻撃が頻発し、負荷によるダウンが発生していた

|--- |--- |
| プロジェクトA | ToC, ToB |
| プロジェクトB | 社内システム |
| プロジェクトC | 社内システム |
| プロジェクトD | 社内システム |

### 取り組んだこと
#### インフラ全体の現状把握と優先順位の整理
まず、各プロジェクトごとのネットワーク構成を把握し、ユーザー影響が大きい機能の切り分けを行いました。
これにより、どのリソースを優先的に改善すべきかを明確にし、影響範囲の大きいものから順に対応しました。
各プロジェクトごとのネットワーク構成の把握や止まってしまうとユーザー影響の大きい機能の切り分けを一番最初に行いました。
その後、 AWS のバージョンアップ通知やセキュリティホールの穴埋め作業に取り掛かりました。

### RDS バージョンアップ対応（MySQL 5系 → MySQL 8系）
AWSのMySQL 5系のサポート終了に伴い、MySQL 8系への移行を実施しました。

| 項目 | 内容 |
|--- |--- |
| 課題 | 既存のRDSがMySQL 5系のまま放置されており、サポート終了に伴いセキュリティリスクが高まっていた |
| 対応 | - ブルーグリーンデプロイを採用し、ダウンタイム最小化した移行を実現 <br> - データの整合性を担保するため、事前にリハーサル環境での動作検証を実施 <br> - 影響範囲を最小化するため、アプリケーションコードの改修を最小限に抑えた |
| 成果 | - ページのロード時間が 2〜3秒 → 1秒未満に改善 <br> - DBパフォーマンスが向上し、クエリ実行時間が短縮 <br> - サポート料金の停止によりコスト削減 |


### OS 移行（CentOS → AlmaLinux）
CentOSのサポート終了に伴い、OSの移行を実施しました。

| 項目 | 内容 |
|--- |--- |
| 課題 | CentOSのEOLにより、新規のセキュリティパッチ適用が不可能になり、脆弱性リスクが高まっていた |
| 対応 | - 影響を最小限に抑えるため、AlmaLinux への移行を選択 <br> - 事前検証環境を構築し、アプリケーションの動作確認を実施 <br> - 本番環境のダウンタイムを抑えるため、ローリングアップデートを採用 |
| 成果 | - 最新のセキュリティパッチを適用可能に <br> - OSのEOL問題を解消し、安定稼働を確保 |


### DoS攻撃対策
アプリケーションサーバーに対するDoS攻撃が頻発し、サーバーダウンが発生していたため、セキュリティ対策を強化しました。

| 項目 | 内容 |
|--- |--- |
| 課題 | - ALBを介さず、直接アプリケーションサーバーにアクセスされることで負荷が集中 <br> - セキュリティグループの設定が適切でなく、不正アクセスのリスクが高まっていた |
| 対応 | - ALB のリスナールールを最適化し、すべてのトラフィックを適切に制御  <br> - セキュリティグループの見直しを実施し、不正アクセスのリスクを低減 |
| 成果 | - アプリケーションサーバーの負荷が軽減し、ダウンタイムが発生しなくなった <br> - 攻撃トラフィックを大幅に削減し、安定稼働を実現 |

## 介護求人サイト
### プロジェクト概要

| 項目 | 内容 |
|--- |--- |
| 期間 | 2023年4月 〜 現座 |
| プロジェクトカテゴリ | Webサービス / 自社プロダクト |
| プロジェクト概要 | 介護業界の人材難を解消するべく立ち上がったプロジェクト。求人を提供する事業所及び介護求人を探す求職者を繋ぐプラットフォーム。 |
| 担当工程 | 設計<br>コーディング<br>運用保守 |
| ロール / 職種 | メンバー / バックエンド, フロントエンド, インフラ |
| 開発体制 | Developer: 5人<br> Biz: 15人 |
| 開発手法  | スクラム |
| 技術スタック | フロントエンド:<br>- jQuery<br>- Vue.js<br>- TypeScript<br>- Bootstrap4<br>- SCSS<br>バックエンド:<br>- CakePHP4 (PHP8.2)<br>インフラ:<br>- AWS (EC2, RDS, SQS, S3)  |
| テスト | UT: Codeception/Vitest<br>E2E: Codeception |
| 周辺ツール | 管理ツール： Mackerel<br>コード管理： GitHub<br>タスク管理： GitHubProjects, Notion<br>数値計測： Redash, GA4, Microsoft Clarity  |

### 課題
本プロジェクトは長らく赤字経営が続いており、開発体制の変革が求められていました。そのようなタイミングで私がジョインし、新規メンバーと既存メンバーの協力体制を構築。結果として開発サイクルの改善を実現し、赤字経営からの脱却につなげました。

### 取り組んだこと
#### チーム間の関係構築
変革期にジョインしたため、まずは既存メンバー（Devチーム / Bizチーム）との関係構築を優先しました。開発業務が主軸ではありますが、チーム開発ではメンバー間の信頼が不可欠であると考えたためです。

その結果、Bizメンバーからユーザー目線でのシステム改善提案が積極的に上がるようになり、チーム間の確執も生まれることなく、スムーズな開発体制を築くことができました。

####  既存技術（CakePHP）のキャッチアップと開発効率の向上
バックエンドにはCakePHP 4が採用されており、現在では利用者が少なく、公式ドキュメントにも誤りが見られることがありました。そのため、開発を進める上でソースコードレベルでの調査が必要になる場面も多くありました。
しかし、効率的にキャッチアップを進め、開発スピードを落とすことなく業務に貢献しました。
### 成果
Joinして1年1ヶ月後に単月黒字までプロダクトを成長する事ができました。

- 全ての案件を独自フレームワークを用いり、リリースまでのスピードを最大化

### 成果
- すべての案件を納期内にリリースし、延期を発生させなかった。
